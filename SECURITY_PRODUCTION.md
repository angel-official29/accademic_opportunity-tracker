# Production configuration

The current local server is hardened for HTTP on loopback. External production hosting was not deployed or tested by this audit.

1. Use Python 3.11+ and MySQL **8.0.29+**. The installed/reviewed server is MySQL 8.0.46. Install pinned runtime dependencies from `requirements.txt`. Schema/migration changes require an independent privileged account and a backup; MySQL DDL/grants commit implicitly.
2. Use `.env.production.example` as a placeholder-only reference. Configure an unpredictable private `FLASK_SECRET_KEY` of at least 32 characters, a dedicated non-root `DB_USER`/password, `APP_ENV=production`, and exact comma-separated `TRUSTED_HOSTS`. Startup rejects absent/short/example secrets and production root/missing-host configuration. Do not use a source-controlled/shared key.
3. Production forces Secure/HttpOnly/SameSite=Lax cookies and requires HTTPS. Sessions have an eight-hour absolute server-side expiry; logout revokes the current token's digest. Development deliberately keeps Secure disabled so local HTTP login works. Signed cookies carry no password, hash, full name, academic profile or authoritative role.
4. Serve with Waitress behind a properly configured TLS proxy. A loopback backend example is `waitress-serve --listen=127.0.0.1:5000 --url-scheme=https app:app`. Only assert `--url-scheme=https` when a trusted TLS terminator is the sole caller; direct public HTTP to that backend would defeat the HTTPS check. Restrict backend access and do not trust arbitrary client forwarding headers. No ProxyFix is enabled.
5. The runtime user has SELECT/INSERT on users and student_profiles, SELECT on departments, and SELECT/INSERT/UPDATE on auth_sessions and security_rate_limits. It has no access to unrelated opportunity/application tables, root, DDL, GRANT, account updates or destructive deletes. Expand grants only when future implemented workflows need them, following a new review.
6. Migration credentials in local `.migration.env` preserve the pre-audit privileged account without changing its password. **For production, move these credentials outside the web process's readable directory and use a separate operations identity/secret store.** A web process with arbitrary local file access could otherwise recover those credentials despite runtime least privilege. The audit applied Windows owner/SYSTEM-only ACLs to `.env` and `.migration.env`; that does not remove existing OneDrive/cloud copies or protect against compromise of that same OS user.
7. Keep MySQL private. A remote database deployment needs verified TLS and host-scoped grants, configured explicitly before use. The connector currently targets the configured local database and does not implement a remote certificate-verification policy.
8. Disable or tightly restrict developer diagnostics; `/database-test` now requires active admin authentication and reveals only generic availability. No admin password is hard-coded; use the interactive hashed-password creation script. Do not launch with a Flask debugger/`--debug` in production.

Login limits are 30 attempts/minute per direct client IP and 8/minute per normalized account (UID and matching CU email share the bucket). Registration allows 20/hour per direct IP. MySQL counters are shared across workers and updated under row locks; only HMAC bucket keys are stored. Responses use 429 and Retry-After. X-Forwarded-For is ignored. Fixed windows, shared campus addresses, deliberate account throttling and distributed attacks need operational tuning and edge protections. Counters/session rows are retained under this audit's no-deletion rule; establish a reviewed retention policy before sustained public use.

CSP permits only local assets, forbids object embedding, restricts form/base origins and denies framing. Existing static inline progress widths were moved to CSS classes to preserve appearance without unsafe-inline. Other headers include no-sniff, Permissions-Policy, Referrer-Policy and no-store. HSTS applies only in production HTTPS and does not automatically enable subdomains/preload.

Audit history has rejecting UPDATE/DELETE triggers, and runtime credentials have no history-write access. Existing schema cascades were preserved. MySQL foreign-key cascades do not invoke these triggers; a privileged DBA can still delete parent data or alter the schema. No user-delete route exists and no runtime delete privilege was granted. A future deletion workflow requires a separate retention/integrity design and review.

CU email/UID validation checks format and consistency, not ownership. Existing academic values, skills and readiness remain self-reported or unimplemented. University SSO/email verification, account recovery/MFA, external audit logging, backup/restore, infrastructure patching and TLS/proxy deployment remain operational/product work. An advisory scan reports known package vulnerabilities only and cannot establish that the application or host has no vulnerabilities.
